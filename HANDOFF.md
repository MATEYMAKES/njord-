## What NJORD is

A fictional creative-studio site (client, industry, brand — all invented for this build) whose entire visual identity is one continuous population of ASCII characters that never disappears or respawns — it only ever *retargets* between named formations as the visitor scrolls. Three fictional showcase projects (Aurelia — jewelry, Pulse — music festival, Meridian — fintech) sit inside NJORD as restrained editorial rows, each triggering a full "project page" on click. A fully generative, synthesized-in-browser soundscape (`audio-engine.js`) runs alongside it, its own state morphing with the same scroll timeline — see its own section below. The whole site is bilingual (English / Albanian) via `i18n.js`, with Shqip as the default language.

Deployment: a single Artifact (multi-file: `index.html` + `style.css` + `ascii-engine.js` + `audio-engine.js` + `i18n.js` + `main.js`), published via the `Artifact` tool. ## Architecture — the ASCII organism (`ascii-engine.js`, class `AsciiOrganism`)

This is the core system and the one most iterated on. Key design, current as of the last working version:

- **One particle pool** (~820 desktop / ~420 mobile), each with a fixed *identity* computed once at construction: a Fibonacci-sphere sample + land/ocean flag (globe), a facet index + barycentric uv (diamond), a line index + t-position (wave), a node/edge/ambient role (network). Identity never changes — only which target position is currently being computed for it.
- **Single continuous scroll timeline**, NOT competing weighted zones (an earlier "cubed zone weights" approach was scrapped entirely — see "History" below for why). `_timelineSegment()` finds exactly which TWO neighboring registered anchors (hero→globe, Aurelia→diamond, Pulse→wave, Meridian→network, contact→globe, in that scroll order) the viewport's vertical center sits between, and a smoothstep-eased `t` (0–1) along that one gap. Every particle's target is a pure two-point lerp between those two formations' `_formationTarget()` outputs — never three, never an undefined "cloud" fallback.
- **Formation functions** live in `_formationTarget(name, i, t)`: globe (lit rotating sphere with stylized non-cartographic continent blobs), diamond (8-facet bipyramid, flat-shaded, sparkle highlights), wave (2 lines: 1 strong + 1 fainter echo), network (22 drifting nodes, live nearest-2-neighbor edges recomputed every frame, ~1/5 particles left as free ambient), **constellation** (studio section — a fixed, deliberately non-animated 9-node graph + connecting edges, seeded identically (`mulberry32(11)`) to the small standalone decorative canvas it replaced; the only formation with no motion of its own beyond the universal jitter wobble, and the only one besides globe that uses the site's own `--signal` acid-green rather than a client-project color).
- **Physics is pure exponential easing everywhere** — `x += (target - x) * 0.045` — deliberately chosen because it mathematically cannot overshoot (no velocity/spring anywhere). Cursor-repulsion is a *second*, separately-eased "desired offset" (not an impulse), so it also cannot bounce.
- **Color**: each formation has an accent RGB and a `c` (color-intensity) weight — globe `c:0` (neutral), diamond/wave `c:1`, network `c:0.4`. The blend color is weighted by each side's own `c`, NOT by raw scroll `t` — this was a real bug (see History). Render does a true continuous `lerp(ink, accent, colorMix)` per particle, no threshold.
- **Tiny organic wobble** (`jitterSeed`) rides on top of the resolved target for texture — not a competing state, can't make anything read as unresolved.
- **Portal transition (`burst`/`unburst`)**: on project click, the organism freezes its normal ticking and explodes the *exact particles already on screen* outward from the formation's own current anchor point while flooding the canvas with the project's accent color (all in white text on the flood). `unburst` runs it backward using the same frozen positions, so it reforms exactly what it was, not a fresh shape.

Also in `ascii-engine.js`: `AsciiField` (generic point-cloud→canvas renderer), `StaticGlyphField` (the "01/02/03" index numbers next to each project row), `FormationPortrait` (standalone denser render of one formation for a project page's own visual panel — see below). `TextureWash` (formerly used for the studio-section diagram) was removed entirely once that diagram became the `constellation` formation above — see "Studio" below.

### Mobile performance (iOS throttling)

iOS Safari throttles sustained canvas work — this organism draws hundreds of individual `fillText` glyphs every frame, exactly the kind of continuous load that trips it (confirmed on an iPhone 12 Pro: organism didn't render at all before this). Fixed by cutting the actual cost on mobile (`window.innerWidth < 720`, both `AsciiOrganism` and `FormationPortrait`), not by detecting/reacting to throttling after the fact:
- Particle count: 820 → 260 (`AsciiOrganism`); `FormationPortrait` (project-page backgrounds) 2600 → 900.
- Canvas resolution: devicePixelRatio capped at 1 instead of 2 — quarters the raster area `fillText` has to cover.
- Frame rate: throttled to ~30fps via a manual accumulator in `_frame()` (skips ticks until enough time accumulates, then uses the *accumulated* dt so motion speed stays correct — only render frequency drops).
- Network formation's O(nodeCount²) nearest-neighbor recompute skipped every other mobile frame.
- Ticker pauses on `document.visibilitychange` (tab hidden) — also avoids building up the sustained load that triggers iOS's throttling in the first place.
- Not yet re-confirmed on device since the separate viewport-meta bug (below) was fixed — worth a fresh check now that mobile testing is actually accurate.

## Services section — procedural ASCII roadmap, V2 (`ascii-engine.js` `roadmap` formation, `main.js`, `index.html`, `style.css`)

- Replaced the original hover-reveal ledger (five `.service-row` rows, plus a `#service-modal` tap-to-open-page pattern built earlier the same session) entirely — that whole system read as flat next to the rest of the site and is superseded, not extended. The old version is fully preserved: `versions/v1-services/` has copies of the four files it touched, and it's also recoverable from the project's own git history (`git log`, this redesign starts from the "Baseline: NJORD before Services V2 roadmap redesign" commit) or from artifact version 55.
- **`roadmap` is a sixth organism formation**, registered in `main.js`'s `organism.setZones([...])` between `network` (Meridian) and `constellation` (Studio) as `{ name: 'roadmap', el: document.getElementById('services'), ranged: true }` — the same persistent particle pool as every other formation, not a second canvas, per an explicit requirement that the *existing* artwork transform rather than a new one appear.
- **Ranged zones** are a new concept in `_timelineSegment()` (`ascii-engine.js`): every other zone is a single pivot point (docY = its element's vertical center) that two neighboring formations blend across. `roadmap` needed the opposite — full resolution across the *entire* Services section's scroll height, not an instant pivot, since five nodes have to reveal in sequence as you scroll through it. A zone flagged `ranged: true` contributes two points sharing its name (element top and element top+height) instead of one; the segment *between* those two points resolves as a same-ends `roadmap→roadmap` span for the section's whole height, while the normal pairwise blend still handles the approach (from `network`) and exit (to `constellation`) on either side exactly like every other formation. That span additionally computes `seg.localT` — linear (not smoothstepped) 0–1 progress through the section, used for the path-growth/typing mechanic below. During the approach/exit blends, `localT` is forced to `0`/`1` respectively (entering reads as "just starting," leaving reads as "fully finished") rather than being left undefined.
- **Node/path layout is genuinely randomized, not seeded** (`AsciiOrganism._generateRoadmapLayout()`, called once in the constructor) — deliberately the one exception to every other formation's `mulberry32`-seeded stability, per an explicit "different every refresh" requirement. Five nodes get evenly-spaced y (order must always read top-to-bottom) and randomized x within a band (desktop 18–82% width, min separation 14%; mobile — `window.innerWidth < 720`, the same threshold used throughout this file — 38–62%, min separation 8%, tighter per "mobile should have much less horizontal variation") with retry-on-violation. Positions are stored as normalized 0–1 fractions, not px, so a resize (including the iOS toolbar-driven resize documented elsewhere in this file) reflows proportionally instead of re-rolling — that's what "fixed during the session" means here. The connecting path is a 17-point polyline (`roadmapSeeds`) — each node plus 3 perpendicular-jittered intermediate points per segment, so it bends rather than running straight.
- **Per-particle reveal** (`_formationTarget`'s `'roadmap'` case): each particle has a fixed identity `roadmapU` (0–1 position along the path, computed once, same "identity never changes" rule as every other formation) and a fixed `roadmapDensity`. A particle only renders on the path once `roadmapU[i] <= seg.localT` — that inequality is the entire "grows as you scroll" mechanism; particles behind the threshold sit faintly at the path's own start instead of popping in. Node-proximity gets an intensity boost (`nodeCloseness`) so each of the five points reads as a place the path *arrived at*, not just a label floating near it. After the route is fully traversed and the exit blend actually starts (`seg.a==='roadmap' && seg.b!=='roadmap'`), particles gain growing scatter + fade keyed to `seg.t` — the explicit "loses structure and disperses" dissolve, layered on top of (not replacing) the ordinary cross-formation blend.
- **Text is real DOM, not canvas** (`main.js`, the "Services — procedural ASCII roadmap" block) — five `.roadmap-node` elements (`index.html`) positioned via the same `roadmapNodes` fractions the organism generated, each with a heading and support line typed in directly from scroll position: `charsShown = round(text.length * clamp01(progress))`, recomputed every scroll frame from `organism.seg`/`seg.localT` — never a CSS transition or `setTimeout` sequence, so scrolling back up un-types symmetrically, matching the path's own reversal. Heading completes before the support line starts (`headingProgress`/`supportProgress` split a node's own progress window in half). Each node also carries an always-complete `.roadmap-node__sr` (visually hidden) for screen readers, independent of the sighted per-character reveal — content stays real/accessible HTML per the brief, only the connecting path is canvas.
- **Reduced motion**: mirrors how every other formation already degrades (`AsciiOrganism.start()`'s existing `reduced` branch freezes the whole organism at one settled frame, not just roadmap) — the DOM typewriter skips its scroll-driven path entirely under `prefers-reduced-motion` and shows every node's full text immediately instead, no cursor animation.
- Content (`services.01–05.title/.desc` in `i18n.js`, bilingual EN/SQ): 01 Branding & Identity, 02 Website Design & UI/UX, 03 Back-End Development, 04 Local Hosting, 05 SEO & Ongoing Support. Each node's markup has a visible `.roadmap-node__num` label ("01"–"05") plus heading/support/cursor.
- **Canvas/DOM coordinate matching**: `_formationTarget`'s `'roadmap'` case computes each particle's ABSOLUTE on-screen position from the section's real, currently-scrolled `getBoundingClientRect()` (cached once per frame as `this._roadmapRect` in `_timelineSegment()`) — the same math `main.js` uses to place the real `.roadmap-node` text — then back-solves the local `fx`/`fy` the usual anchor formula needs to land exactly there. This is load-bearing: every other formation is compact (fits in roughly one viewport around a single anchor), but this section spans `.roadmap-nodes`' real `min-height: 420vh`, so the ordinary anchor-relative offset can't represent it — without this, the canvas path and the DOM text drift apart as you scroll.
- **Node-text legibility**: density is DAMPENED (not boosted) in a radius around each node's exact position, since the real text sits exactly there — see `textClearance` in `_formationTarget`.
- **Density warp must stay monotonic.** The per-particle density-variation warp (`roadmapU[i] = raw + amplitude*sin(raw*π*frequency)`) folds onto overlapping output values — producing a hard density spike instead of gentle texture — whenever `amplitude*frequency` exceeds 1. Currently `0.08 * 3.1π ≈ 0.78`, safely under. If either constant is retuned, keep their product under 1 (a real bug: an earlier 0.15 amplitude produced a visible density spike right around node 2).
- **The DOM typewriter's reveal timing is driven by each node's own `getBoundingClientRect()`** every scroll frame (`TYPE_START_FRAC`/`TYPE_END_FRAC` in `main.js`, 0.8→0.35 of viewport height), not by slicing the organism's `seg.localT` into per-node bands — ties it exactly to real on-screen position regardless of container height, and reverses cleanly on scroll-up since there's no state, just a fresh recompute every frame.
- This project has a git repo now (it didn't before this redesign) — `git log --oneline` in the project root has one commit per implementation task/fix, useful for bisecting if something in this system needs isolating later.
- **Still not confirmed on a live device/browser** — every fix in this system so far has been verified via isolated Node scripts (coordinate math, timeline segment logic, warp monotonicity) rather than by looking at a live render, since the Chrome extension hasn't been connected in any session that touched this code. First real check should cover: numbers visible on all 5 nodes, the path tracking/growing in sync with the text (not lagging or detached), the last node getting comfortable on-screen time before the exit transition, and text staying legible against the path at every node.

- **Every visible string on the site has an English and an Albanian (Shqip) translation.** Shqip is the default/standard language (`DEFAULT_LANG = 'sq'` in `i18n.js`) — English is what the toggle switches *to*, not the default.

- If new translatable content is ever added: add the string to both `en`/`sq` in `i18n.js`'s `translations` object, then either tag the static element with the right `data-i18n*` attribute, or call `t('the.new.key')` directly if it's JS-generated. Don't hardcode a new English string directly in `index.html` or `main.js` — it'll silently never translate.

## Audio variants — A1 vs A2 (`audio-engine.js` vs `audio-engine-a2.js`)

There are now **two** complete, drop-in-compatible implementations of the generative audio system, both exporting an identical-API `GenerativeAudio` class (`attachOrganism`, `enable`, `disable`, `toggle`, `destroy`, `getPulseWaveform`) — `main.js` imports whichever one is currently live from a single line:
```js
import { GenerativeAudio } from './audio-engine-a2.js'; // or './audio-engine.js' for A1
```
- **A1** (`audio-engine.js`) is the original build described below — the user's verdict on it was "I love all the ideas, but it's too eery." **Left completely untouched, per explicit instruction not to delete anything** — it's a full working alternative to revert to by changing that one import line back, not dead code.
- **A2** (`audio-engine-a2.js`, currently the live one) is a same-architecture, retuned sibling built specifically to address "too eery" while keeping "the same patterns." Every class (`GlobeVoice`, `CloudVoice`, `AureliaVoice`, `PulseVoice`, `NetworkVoice`, `Scheduler`, `GenerativeAudio`) and the whole weight-mapping/`_poll()` mechanism is structurally identical to A1 — only the tonal/timbral *numbers* changed:
  - **Scale**: A1's `SCALE = [0,2,3,7,9,10]` (an ambiguous 6-note set, no major 3rd — this ambiguity was likely the single biggest contributor to "eerie") → A2's `SCALE = [0,2,4,7,9]`, a plain major pentatonic. No minor or dissonant interval is even possible in this set.
  - **Root**: A1 `ROOT_HZ = 55` (A1, dark sub-bass) → A2 `ROOT_HZ = 110` (A2, one octave up).
  - **Reverb**: A1 was long and wet (4.2s decay-exponent 2.6, `reverbGain 0.55`) → A2 is shorter and drier (2.6s decay-exponent 3.4, `reverbGain 0.35`, `dryGain 0.9`) — an airy room instead of a long dark cave.
  - **Master filter**: A1 base cutoff 5200Hz → A2 6800Hz (brighter overall).
  - **Pacing**: every voice's event timing was tightened (e.g. Globe's swell interval 18–34s → 10–18s, Aurelia's ping decay 1.2–3.2s → 0.8–2.0s with ~2x the trigger rate, Network's swells 3–8s → 2–5s, Pulse's step grid 0.72s → 0.55s) — A1's long silences between sparse events were part of what read as "held-breath eerie"; A2 stays restrained but noticeably more present.
  - **Aurelia's comb feedback** (the "glass" resonance) reduced 0.42 → 0.3 — less deep/ghostly ringing, cleaner shimmer.
  - Constants that only affect *where in the scale* something lands (the various `pick(rnd, [...])` index arrays) were left alone in most voices — they're safe regardless of scale length since `degreeHz()`'s modulo logic re-quantizes any index into whatever `SCALE` is active. Only touched where a genuinely different register/character was wanted (Aurelia, Network).
- If further audio iteration is requested, keep editing whichever file is currently imported in `main.js` (check that line first) — and if the user asks for "A3" or similar, follow the same pattern: copy the current live file to a new sibling, tune it, swap the one import line, leave the previous file(s) untouched.
- **Post-launch tuning, applied directly to A2 (not a new variant)**: `CloudVoice.setWeight()`'s bus-gain ceiling cut from `0.8` to `0.32` — a straight 60% loudness reduction of the CLOUD voice specifically (the noise-grain "whoosh" that plays during transitions between formations), per user feedback that it was too loud. Nothing else about Cloud changed (density, grain duration, register, scheduling are untouched) — this only scales how loud it gets at full weight. If asked to further adjust any single voice's loudness in isolation, this is the pattern: each voice's `setWeight()` has exactly one such ceiling constant multiplying `this._weight` into `bus.gain` — scale that one number, don't touch the per-event `peak` calculations inside `_grain`/`_ping`/`_step`/`_tick`, since bus gain and per-event peak multiply together and changing bus gain alone already scales the whole voice uniformly.

## Architecture — the generative audio engine (`audio-engine.js`, class `GenerativeAudio`)

One persistent, fully synthesized-in-browser soundscape (oscillators, generated noise, filters, envelopes, code-built reverb — no audio files anywhere) whose state morphs continuously with the ASCII organism's own scroll timeline, mirroring the organism's own "never restart, only crossfade" philosophy.

- **Harmonic system**: everything pitched routes through `degreeHz(index, octave)`, which quantizes to one shared root (`ROOT_HZ = 55`, A1) + six-note scale (`SCALE = [0,2,3,7,9,10]` — deliberately missing a perfect 4th so it reads as open/unresolved rather than a conventional minor scale). This is the single mechanism that keeps five independently-scheduled voices harmonically coherent without ever coordinating on pitch directly — if new pitched material is added anywhere, route it through `degreeHz()`, don't compute a raw Hz value by hand.
- **Five persistent voices**, one per formation plus one for transitions, each its own class in `audio-engine.js`, each with a `bus` gain node whose target is smoothly set every ~90ms by `GenerativeAudio._poll()`: `GlobeVoice` (spacious drifting drone + rare long swells), `CloudVoice` (bandpass-filtered noise grains — the "in-between" texture), `AureliaVoice` (comb-resonant glass pings via a short feedback delay tuned to a scale-degree period), `PulseVoice` (a generated Euclidean-style rhythm of soft tone+noise ticks, reshuffled occasionally, plus a very quiet continuous carrier tone), `NetworkVoice` (5 independent panned long-tone "nodes" that wake/fade individually and occasionally swell in correlated pairs).
- **No hard starts/stops between formations.** All oscillators for all voices are created once (in `GenerativeAudio._build()`, itself only called once on the *first* `enable()`) and simply run continuously at near-zero gain when their formation isn't active; only each voice's `bus.gain` is ramped via `setTargetAtTime`. This is the audio equivalent of the organism's own particle-identity-never-changes rule.
- **Timing is intentionally never a fixed loop.** Each voice runs its own `Scheduler` (a standard Web-Audio lookahead scheduler — `setTimeout` polling, sample-accurate `AudioContext.currentTime` scheduling) whose `tick` callback both plays the next event *and* returns a randomized wait until the next tick; several LFOs also run at mutually-unrelated slow rates (0.015–0.07Hz). Nothing here should ever be refactored into a fixed-length bar/pattern that repeats verbatim — that was an explicit requirement (no audible loop within a 10-minute visit).
- **Weight mapping** (`GenerativeAudio._poll()`): reads the organism's own public `seg = {a, b, t}` (which formation pair the scroll timeline is currently between, and how far along) — `weightOf(name)` gives each named formation's voice its crossfade weight directly from `seg`; `cloudWeight = 4*t*(1-t)` when `a !== b` (0 at rest, peaking mid-transition) drives `CloudVoice`, which also gets a floor from `org.scrollTurbulence` so fast scrolling adds grain texture even while resting on a formation.
- **Sparse, selective visual coupling** — deliberately not exhaustive: `org.pointerSpeed` (cursor speed) nudges a shared master lowpass filter brighter and increases Aurelia/Cloud event density slightly; `org.scrollTurbulence` feeds Cloud's grain density and Network/Aurelia's event rate. No per-click, per-particle, or per-formation-detail sound effects — the coupling is meant to read as subconscious, not literal.
- **PULSE's ASCII wave is audio-reactive, not faked.** `PulseVoice` is routed in series through a dedicated `AnalyserNode` (`GenerativeAudio.getPulseWaveform()` calls `getFloatTimeDomainData` on it) before reaching the master bus. `AsciiOrganism.setWaveformSource(fn)` (called once from `main.js`) injects that getter; the `wave` case in `_formationTarget()` blends the real sample data in with the original synthetic sine (roughly 70/30 audio/synthetic) so the line degrades gracefully to its old look when sound is off or quiet, but genuinely reflects the generated audio when it's on. The `* 10` gain-compensation multiplier on the raw sample (`ascii-engine.js`, wave case) is a first-pass estimate for how quiet `PulseVoice`'s own bus typically is — untested visually, first thing to retune if the wave looks too flat or too extreme.
- **Autoplay policy**: `GenerativeAudio` never touches `AudioContext` until `enable()` is called, which only ever happens from the sound toggle's click handler (`main.js`) — a real user gesture. Toggling off ramps `master.gain` down over 1.2s then `ctx.suspend()`s (not `close()`s) so toggling back on is instant and doesn't rebuild the whole graph; the graph is only fully torn down (`destroy()`, stops every oscillator, `ctx.close()`) on `pagehide`.
- **Gain safety**: every gain node starts at `0.0001` (never literal `0`, so exponential ramps stay valid) and every audible change goes through `linearRampToValueAtTime`/`setTargetAtTime` from the node's *current* value (`cancelScheduledValues` + `setValueAtTime(current)` first) — never a direct `.value =` jump on an in-use gain. Master volume target is a conservative `0.32`, behind a `DynamicsCompressorNode` safety limiter and a code-generated convolution reverb (`makeImpulse()` — noise shaped by an exponential decay envelope, not a recorded IR).
- **UI**: `.sound-toggle` (`index.html`/`style.css`), fixed bottom-left, `z-index:650` (above the project modal's 600, so sound can always be switched off from any page). Plain `<button>` with `aria-pressed`, so it's keyboard-operable by default with no extra JS needed.
- **Reduced motion**: `GenerativeAudio` reads the same `prefersReducedMotion()` export ascii-engine.js already uses, and damps a couple of LFO/modulation depths (Globe's detune LFOs, Cloud's grain-rate scaling) by ~30-40% when it's set. This is a light-touch accommodation, not a silent mode — sound is still opt-in either way via the toggle.

## Self-hosting outside claude.ai

`index.html` is deliberately a body-only *fragment* — no `<!DOCTYPE>`/`<html>`/`<head>` — because the Artifact tool wraps it with a proper skeleton (including the viewport meta tag) at publish time. The production site at the claude.ai artifact URL has always had that wrapper; it's never been affected by anything below.

**Never serve `index.html` raw with a bare static server** (e.g. `python -m http.server`) — without the wrapper there's no `<!DOCTYPE>` and no viewport meta tag, so iOS Safari renders the page as a ~980px desktop layout and zooms it out to fit the screen. Everything looks "shrunk," and CSS changes appear to do nothing, because the whole page is being scaled down uniformly rather than rendered at its real size — this looks exactly like a font-size problem but isn't one. Use `_dev_server.py` in the project root instead (`python _dev_server.py`, port 8080): reads `index.html` fresh from disk on every request, wraps it with the missing `<!DOCTYPE>`/`<head>`/viewport-meta skeleton, and sends `Cache-Control: no-store` on everything (Mobile Safari caches aggressively enough to mask a fix otherwise). Confirmed fixed on-device. Every other file (CSS/JS) is served normally; only `/` and `/index.html` get wrapped.

## Mobile typography (`style.css`, `@media (max-width: 640px)` right after the `:root` blocks)

Every `clamp(min, Nvw, max)` in the stylesheet — the root type tokens (`--fs-hero`, `--fs-display`, `--fs-h2`, `--fs-lead`, `--fs-body`, `--fs-small`, `--fs-micro`) and seven individually hardcoded ones (`.hero-descriptor`, `.work-row__title`, `.service-row__title`, `.contact-head h2`, `.contact-email`, `.project-modal__title`, `.project-modal__tag`) — used a `vw` preferred value smaller than its own minimum at phone widths (~390px), so every one of them silently bottomed out at a minimum tuned for "narrow desktop," never actually scaling up for a phone.

Fixed with a `max-width: 640px` block: bigger minimums + fresh `vw` coefficients for the root tokens (reaches anything using `var(--fs-*)`), plus separate overrides for the seven hardcoded selectors above (they don't reference the root tokens, so need their own fix). Current mobile values: `--fs-micro` 11px→16px, `--fs-small` 13px→17px, `--fs-body` 16px→18px — pushed hard on the small end specifically, since that's nav/eyebrows/tags/toggles/meta text, the class of element users actually zoom in for. Toggle/tag padding is `em`-based so it scaled up automatically, no separate fix needed there.

**If a new heading/label is added anywhere with its own hardcoded `clamp(min, Nvw, max)`: check whether `min` exceeds the preferred value at ~390px width — if so it has this same bug and needs its own entry in this block**, since the root-token fix doesn't reach selectors with their own hardcoded clamp.

## History — decisions made and why (read before re-tuning)

1. **Original design** used independent `RotatingSolid` objects per section (hero sphere, contact sphere) plus hover-triggered texture washes per project row. Explicitly scrapped when the user demanded ONE continuous organism that never disappears/respawns.
2. **First organism version** used per-zone `resolve` values summed/maxed with cubed weighting to blend multiple nearby "zones." This caused persistent, hard-to-fully-tune problems: muddy blends between adjacent projects, an unwanted "filler" cloud state between projects, and spacing-sensitivity (needed ever-larger buffers between rows to stay clean). **Scrapped entirely** and replaced with the single continuous two-point timeline described above, on the user's explicit "start again from scratch, focus on smoothness" instruction. This fixed the class of problem structurally rather than by tuning constants — don't reintroduce a multi-zone weighting scheme.
3. **Cloud state removed.** There is no more independent "loose particle cloud" formation/mode — between any two named formations, particles interpolate directly. A tiny decorative wobble remains but is not a competing state.
4. Physics went from velocity/spring-based (could overshoot → user called it "cartoonish bounce") to pure exponential easing (cannot overshoot by construction) for both position-approach and cursor-avoidance.
5. Portal entry went from a disconnected generic texture-wash "burst" + separate CSS-fade modal → FLIP scale-transform-from-row-rect + organism burst → **current**: radial clip-path-from-click-point + organism burst, page background matching the ASCII color. Each iteration was a direct response to specific user feedback ("not smooth," "I want it to feel like the section itself expanded," "radially from the point of the click, not a fade").
6. **Real bug fixed (yellow flash):** the color blend used raw scroll-`t` instead of each formation's own color-intensity weight, so globe's (unused, meant-to-be-neutral) yellow-green accent leaked into the hero→Aurelia transition; combined with a hard opacity threshold in the render step (jump to 60%+ opacity the instant `colorMix` crossed 0.03), this caused a visible yellow flash leaving the hero. Fixed by weighting color blend by each side's `c` value and replacing the threshold with a true continuous lerp. If any other formation transition ever shows an unexpected color tint, check this same mechanism first.
7. Meridian's network was made denser (more nodes, more edges per node) and then tightened (smaller spread, smaller wander radius) after feedback that "more cluttered" didn't fix "airy" — density and spread are separate knobs, both needed adjusting.
8. Diamond was rendering upside-down (long pavilion point at top instead of bottom) — a real sign-convention bug in `buildDiamondFacets()` (canvas Y increases downward; the short crown needs negative Y, long pavilion positive Y). Fixed by flipping the vertex Y signs.
9. **Real bug fixed (close transition looked "choppy" vs. the smooth open).** `_burstFrame()` (`ascii-engine.js`) renders two colored layers behind the modal's own CSS clip-path: a full-canvas flat-color `fillRect` and the white ASCII particles on top, each with its own alpha formula written in terms of `eased` (an ease-out curve over `p`, the "how exploded is the formation" value, 0→1 during `burst()`). `unburst()` reuses the exact same code but runs `p` from 1→0 instead — and since the alpha formulas weren't symmetric under that reversal, the flat-color flood stayed near-fully-opaque for almost the whole close animation and only cleared in the last instant, while the modal's clip-path was collapsing smoothly the entire time — the two layers were badly out of step, which is what read as "choppy" (reported by the user as: solid fill smooth, "gradient" fill on top not clearing until the last second). Fixed by introducing `revealEased`, computed from a direction-normalized `revealT = dir>0 ? p : 1-p` (always 0→1 over *this* call's remaining lifetime, regardless of which way `p` is moving) and used only for the two color-alpha values — `spread` (the particle-scatter distance) still correctly reads raw `eased`/`p` directly and was never part of this bug, since scatter-outward-on-burst/pull-together-on-unburst is supposed to track literal explosion-amount, not elapsed-time-of-this-call. **If burst/unburst is ever re-tuned, keep this distinction in mind: anything about "how far exploded are we" should use `p`/`eased` directly; anything about "masking the start of whichever direction is currently running" (the two color alphas) must use `revealEased`, not `eased`.**
